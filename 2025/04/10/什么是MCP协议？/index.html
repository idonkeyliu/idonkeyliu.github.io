什么是MCP协议？

发表于 2025-04-10 |

如果大模型是大脑，那文件、数据库、浏览器、内部 API 就是外设。过去每接一种外设都要私有适配——Agent 与 IDE 重复造轮子。MCP（Model Context Protocol）想提供统一插口，所以常被叫作「AI 应用的 USB-C」。

一句话：Tool Calling 让模型说出「我想做什么」；MCP 让应用用统一方式找到并执行「谁能做」。

这个比喻好用，也要补刀：USB-C 统一的是连接，不保证外设可靠或安全；MCP 也不会自动让模型变聪明。

MCP 解决什么问题

一个 Agent 想读取代码、查询数据库、创建工单，传统做法通常是：

  1. 为每个系统写 HTTP SDK；
  2. 手工把接口描述转换成模型工具 Schema；
  3. 各自处理认证、连接、错误和版本；
  4. 换一个 AI 客户端，再重接一次。

这会形成 M 个 AI 应用 × N 个数据源 的适配矩阵。MCP 把连接边界标准化：工具提供方实现 MCP Server，AI 应用实现 MCP Client，双方按统一协议发现能力和交换消息。

它主要标准化的是：

  • 如何建立连接并协商能力；
  • 如何列出和调用工具；
  • 如何发现和读取资源；
  • 如何提供可复用提示模板；
  • 如何传递结果、错误、进度与取消信号。

它不规定模型必须如何推理，也不是一个 Agent 框架、向量数据库或远程执行沙箱。

Host、Client、Server

MCP 采用三层角色：

角色 职责 例子
Host 面向用户的 AI 应用，管理模型、权限与多个连接 桌面助手、IDE、Agent 平台
Client Host 内的协议客户端，与某个 Server 保持会话 IDE 中的 GitHub MCP 连接
Server 暴露工具、资源和提示的能力提供者 文件系统、数据库、工单 Server

一个 Host 可以连接多个 Server，通常为每个 Server 创建一个 Client 会话。Host 是安全边界的中心：它决定向模型暴露哪些能力、何时征求用户同意、哪些数据可以发给外部服务。

Server 不等于一台独立机器。它可以是由 Host 通过标准输入输出启动的本地进程，也可以是通过网络访问的远程服务。

三种核心原语

Tools：可执行动作

Tool 是模型可以请求调用的函数，例如：

Client 可通过 tools/list 发现工具，通过 tools/call 调用。Tool 可能产生副作用，如发邮件、改工单、执行部署，因此 Host 应展示意图、校验参数，并对高风险动作要求确认。

在 MCP 的交互理念里，Tools 常被描述为 model-controlled：模型可根据任务选择是否调用；但最终执行权仍在 Host 与用户手中。

Resources：可读取上下文

Resource 是由 URI 标识的数据，例如文件、数据库 Schema、知识库文档：

Client 可列出资源、读取内容，也可在 Server 支持时订阅变化。Resource 更像“可放进上下文的资料”，通常由应用决定何时选择和展示，因此常称 application-controlled。

Prompts：可复用交互模板

Prompt 是 Server 提供的参数化消息模板，例如“审查当前 diff”“总结故障报告”。Client 可以列出并获取模板，再由用户显式选择或通过界面触发，因此常称 user-controlled。

Prompts 不是偷偷覆盖系统提示的后门。Host 应让用户知道模板来源与内容，并决定如何组合进最终对话。

三者怎么选

需求 优先选择
执行搜索、查询、写入等动作 Tool
暴露可寻址、可浏览的数据 Resource
提供标准工作流入口或消息模板 Prompt

同一能力有时可以同时提供 Resource 与 Tool。例如“读取日志文件”适合 Resource，“按条件检索海量日志”更适合 Tool。

协议如何运行

MCP 消息基于 JSON-RPC 2.0，包含 Request、Response 和 Notification。连接建立后，不是立刻调用工具，而是先完成生命周期握手：

双方通过 capability negotiation 声明自己支持什么。Client 不应假设所有 Server 都支持 tools、resources、prompts、日志或订阅。

常见传输方式：

  • stdio：Host 启动本地 Server，通过 stdin/stdout 收发消息；简单且适合本地集成。
  • Streamable HTTP：面向远程 Server 的现代 HTTP 传输，可支持流式响应与会话。

早期版本常见的 HTTP + SSE 传输已被 Streamable HTTP 取代为主线方案；实现时应以双方协商的协议版本为准，而不是假设“装了 MCP 就都兼容”。

stdio Server 的 stdout 是协议通道，不能随便 print 调试文本，否则会破坏 JSON-RPC。诊断日志应写 stderr。

一次工具调用的完整流程

假设用户问：“查一下北京天气，并判断要不要带伞。”

重要事实是：模型并不直接讲 MCP。通常由 Host 把 MCP 工具转换为模型厂商的 Tool Calling 格式，再把模型提出的调用转成 MCP 请求。模型负责选择，Host 负责编排，Server 负责执行。

Server 也能向 Client 请求能力

MCP 不完全是单向的。根据能力协商，Server 还可请求 Client 侧能力：

  • Sampling：Server 请求 Host 代表它发起一次模型生成；模型选择和授权仍由 Host 控制。
  • Elicitation：Server 请求通过 Host 向用户补充结构化信息或确认。
  • Roots：Client 告诉 Server 允许操作的文件系统或工作区根范围。

这些能力强化了交互性，也扩大了信任边界。Server 发起 sampling 不应获得模型密钥；敏感输入的 elicitation 需要清晰 UI，不能伪装成普通提示。

MCP 与相邻概念的区别

MCP vs 模型 Tool Calling

Tool Calling 是模型 API 的交互能力：模型输出“想调用哪个函数及参数”。MCP 是应用与外部能力之间的协议。

两者互补，不是替代关系。没有 MCP，Host 也可以直接执行本地函数；没有模型 Tool Calling，应用也可以让用户手动触发 MCP Tool。

MCP vs REST API

REST 定义某个服务的业务接口；MCP 在其上提供适合 AI 应用的发现、Schema、会话和能力协商。Server 内部通常仍会调用 REST、数据库或 CLI。

MCP 不是说 REST 过时了，而是给 AI Host 一个统一适配层。

MCP vs Agent 框架

LangChain、LangGraph 等负责模型循环、状态、分支、记忆和重试；MCP 负责能力连接。Agent 框架可以作为 MCP Host/Client，也可以把自身能力做成 Server。

为什么它对 Agent 重要

Agent 的能力上限取决于它能安全触达什么。MCP 带来几个直接收益：

  1. 可发现：Host 可动态列出 Server 能力，不必把接口写死。
  2. 可移植：同一 Server 有机会被不同 IDE、桌面助手和 Agent 平台复用。
  3. 上下文统一：工具、资源和提示使用一套生命周期与消息协议。
  4. 边界清晰：Host 统一承接授权、用户确认与模型交互。
  5. 生态复用：服务提供方实现一次标准适配，减少重复胶水代码。

但“可插拔”不等于“完全无差异”。不同 Host 的权限 UI、Transport 支持、扩展特性和模型能力仍可能不同，生产接入必须做兼容测试。

与私有工具 API 对比

维度 私有工具集成 MCP
能力发现 应用写死 标准 list/get/call
Schema 各家自定义 统一协议结构
生命周期 自己约定 初始化与能力协商
本地连接 自己管理子进程 stdio 约定
远程连接 任意 HTTP Streamable HTTP
复用性 通常绑定一个应用 可供多个兼容 Host 使用
安全 完全自行设计 有清晰边界，但仍需自行落地策略

如果只有一个稳定接口和一个客户端，直接集成可能更简单。MCP 的价值在于多工具、多 Host、需要生态复用的场景，而不是给每个内部函数再套一层协议。

安全不是协议自动附赠的

MCP Server 本质上能读数据、执行动作，因此应按“不可信插件”对待。

最小权限

  • 文件系统只暴露必要 Roots，默认只读；
  • 数据库使用只读账号或受限存储过程；
  • 写操作拆成细粒度工具，不提供万能 execute_shell；
  • 本地 Server 固定可执行文件与依赖来源。

用户知情

工具描述、参数和副作用应可见。删除、付款、发信、发布等操作必须有明确确认，并使用幂等键防止重复执行。

远程认证

远程 Server 应使用标准认证授权机制，校验 Token 的 audience，禁止 Token 透传给下游。不能把 MCP Server 当开放代理，也不能仅凭“来自内网”就信任请求。

防提示注入

资源内容、工具返回和 Server 提供的描述都可能包含恶意指令。Host 应把它们视为不可信数据：

  • 不让工具结果修改系统权限；
  • 敏感工具按策略过滤，而非仅靠模型自律；
  • 控制返回长度并做内容隔离；
  • 记录每次调用和用户授权；
  • 防范工具名称或描述“投毒”模型选择。

设计一个好 MCP Server

工具要窄而明确

manage_everything(action, payload) 对模型和审计都不友好。优先：

描述中说明何时使用、参数约束、副作用和错误语义。输入使用 JSON Schema，输出尽量稳定、短小并可结构化。

错误要分层

协议错误与工具执行失败不同。参数不合法、工具不存在可返回协议层错误；上游超时、业务拒绝则应作为可理解的工具结果或明确执行错误，让 Host 能决定是否重试。

控制上下文成本

提供分页、过滤、摘要和最大条数；不要让 search_logs 默认返回十万行。Resource 可暴露目录与详情两级结构，Tool 可先返回候选 ID，再按需取详情。

做版本与兼容

协议版本通过初始化协商，业务 Schema 也要独立演进。新增可选字段通常比修改既有字段含义安全；破坏性变化应新建工具名或版本。

实施检查清单

Host/Client 侧

  1. 是否只展示允许的 Server 和能力？
  2. 是否处理初始化、超时、取消、断线和版本不兼容？
  3. 高风险 Tool 是否需要用户确认？
  4. 工具结果是否限制大小并标记为不可信？
  5. 是否有调用日志、耗时、错误率和审计记录？

Server 侧

  1. Tool/Resource/Prompt 边界是否合理？
  2. 输入 Schema 是否严格，错误是否可理解？
  3. 权限是否最小化，凭据是否安全保存？
  4. stdout 是否保持协议纯净？
  5. 写操作是否幂等，是否支持超时与取消？
  6. 是否防 SSRF、路径穿越、命令注入和敏感数据泄露？

小结

MCP 的核心价值不是发明一种新的函数调用，而是把 AI 应用连接外部世界的方式标准化：Host 管理用户与模型，Client 维护协议会话，Server 暴露 Tools、Resources 和 Prompts；双方通过 JSON-RPC、生命周期与能力协商合作。

把它记成一句话：

Tool Calling 让模型表达“我想做什么”，MCP 让应用用统一方式找到并执行“谁能做这件事”。

Agent 越强，权限治理越重要。真正成熟的 MCP 集成，不只要“能连上”，还要可发现、可确认、可审计、可限权、可失败。
